## Product contract

- An endnote is a MyST footnote: a reference `[^label]` in the body and a definition `[^label]: ...`. The syntax, the labels and the MyST node names (`footnoteReference`, `footnoteDefinition`, inline `{ kind: "footnote" }`) are unchanged. No new syntax or metadata is written.
- A definition belongs to the document, not to the block or section it is written after. Several references can share one definition.
- **Definition content**: a native document permits one non-empty paragraph of supported inline content per definition, without footnote references. Multiple paragraphs, other nested blocks or unsupported inline content reject the entire document at admission; there is no source-editing fallback.
- **Endnote order**: the body's blocks first, then the definitions in the order of the first reference to each. Numbers 1, 2, 3, ... follow the same reading order; a repeated reference shows the same number. Labels are identifiers, independent of numbers. During editing, a definition with no reference comes last in its current order, but Save refuses it.
- Canonical Markdown writes the definitions after the body in endnote order, wherever the source or an operation placed them. Non-endnote blocks keep their order and content. Writing the result again gives the same bytes.

## How MyST reads footnotes

myst-parser 1.7.4 uses markdown-it-footnote, which:

- reads every `[^label]: ...` definition first;
- keeps only the last definition of each label, and only when the text references it;
- moves the kept definitions to the end of the tree;
- gives definitions no source position, so myst-parser copies a neighbouring block's position.

A `[^label]` with no definition and an escaped `\[^label]` both become plain text in the AST. Canonical write escapes that text as `\[^label]`; this preserves its parsed meaning.

## Literal syntax diagnostics (#290, #304)

This is the shared source-only diagnostic contract for syntax MyST silently reads as literal text. #304 extends #290's single source-evidence store, diagnostic tokenizer pass and location mapping; it adds no semantic operation or writer behavior.

- Undefined full `[text][label]` / `![alt][label]` and collapsed `[label][]` / `![label][]` references warn. The second bracket must immediately follow the first, as in MyST's link/image rules. Label boundaries and definition lookup use the tokenizer's helpers and normalized reference environment. Shortcut `[label]` and `![label]` never warn: ordinary `[1]` and `[sic]` are intentional prose too. Valid links/images, escaped opening brackets and decoded entities are not candidates.
- Within a valid link's display text, missing reference-link/reference-image shapes are treated as intentional literal text and do not warn. This applies to inline links and reference-style links with an existing definition, including formatted display text. The exclusion is specific to these nested reference shapes: unmatched backticks still warn under the rule below because inline code is meaningful within a link's display text; existing undefined-footnote diagnostics are unchanged. Link destinations/titles and image alt text remain excluded from all literal-syntax diagnostics.
- An unmatched backtick run warns only when immediately followed by non-whitespace content. MyST's existing backtick rule decides whether an equal-length closing run exists within the inline container; the diagnostic observes its literal fallback instead of implementing a code-span parser. Lone runs, runs followed by whitespace/end of container and escaped backticks do not warn. This conservative rule deliberately misses a spaced opener such as `` ` tick ``; an unescaped run attached to content is treated as code intent.
- **Inline math is excluded.** MyST enables `markdown-it-dollarmath` with `allow_space: true` and `allow_digits: true`. Its opener admits both `$x^2` and ordinary `costs $5` / `$ and %`; a failed parse cannot reliably distinguish them. No dollar-only heuristic is added, and parser options are unchanged. These examples remain literal without warnings.
- New `references.unresolved` entries use `{ "syntax": "reference-link" | "reference-image", "label": "missing", "source": "[details][missing]", "path": [1], "line": 5 }` or ``{ "syntax": "inline-code", "source": "`", "path": [3], "line": 9 }``. `source` is the complete reference spelling or the unmatched opening run; code entries have no artificial `label`. Existing `role`, `link` and `footnote: true` discriminants remain unchanged; role/link entries may also carry a MyST lookup failure `reason` as defined in [Section references](section-references-v1.md#scope). Locations retain the container-start contract below; this is not an exact character/line offset for a delimiter on a later line of a paragraph.
- New text warnings identify `reference link`, `reference image` or `inline code`, their source spelling and location, then `has no definition in this document` or `has no closing backtick run; parsed as literal text`. Successful CLI writes/previews append `written as literal text` to these new diagnostics. All source-only kinds share the original-parse capture, `originalWarnings`, exclusions and nonblocking behavior below. Existing footnote wording is preserved.

### Undefined-reference diagnostics (#290)

- Core `unresolvedReferences(document)` also reports unescaped body-text `[^label]` syntax without a matching definition. Labels match exactly, including case, as markdown-it-footnote does. The label must be nonempty and contain no space, newline or closing `]`; this uses the parser's label grammar rather than the narrower authoring-operation label policy.
- The warning names the label, top-level block path and 1-based source start line of its containing inline element (paragraph, table row, etc.), following [Section references](section-references-v1.md#scope). Repeated occurrences are reported separately, including those in headings, formatting, quotes, lists, table cells and captions. Definitions themselves are outside this body-text diagnosis.
- Escaped `\[^label]` is intentional literal text and never warns. Backslash pairs follow the tokenizer's ordinary escape rules. Inline code, code blocks, math, image alt text, link URLs/titles, reference-role targets and other non-text content do not warn. Actual links such as `[^label](url)` remain links; a defined footnote reference does not warn.
- AST inline positions do not retain character offsets or escapes. Core retains the parsed source outside the semantic AST in a `WeakMap`, then uses the existing MyST tokenizer with a diagnostic fallback after its normal inline rules. Escape, code, math, link and valid-footnote rules consume their own syntax first. Bare URLs are excluded using markdown-it's existing URL recognizer even though MyST leaves them as text. Token container lines map back only to actual body text in the parsed snapshot through a line-to-block lookup. The AST, read model, semantic fingerprint and canonical writer are unchanged. Diagnosis is source-only: Core operation clones carry no source evidence, even for unchanged blocks. Text supplied through operations is already literal text, not Markdown syntax to reinterpret.
- CLI `check` exposes these warnings in the existing JSON `references.unresolved` array as `{ "footnote": true, "label": "loss", "path": [1], "line": 5 }`, or on stderr as `warning: footnote [^loss] (block 1, line 5) has no definition in this document`. Warnings alone leave `ok: true`, writeability and exit status 0 unchanged. `check` never writes.
- Every CLI edit, including `format` and `apply-batch`, captures the original parse's report before operations can lose its source evidence. After a successful file commit it prints one stderr warning per original source-only occurrence: `warning: footnote [^loss] (block 1, line 5) has no definition; written as literal \[^loss]`. A batch reports the original source once, not each step's canonical parse. Refused or failed writes print no additional literal-text warnings. Exit codes, stdout (including batch JSON), and written bytes are unchanged. `create` has no original source to diagnose.
- Successful `--dry-run` edits print the same original-source literal-text warnings on stderr, including in JSON mode, after validating the preview without committing. Here `written as literal` describes the canonical preview, not a disk write. JSON previews also include `originalWarnings`: the original source-only entries unchanged from Core (or `[]`). Result `references.unresolved` remains the result document's check report and no longer contains these escaped occurrences. Batch previews report each original occurrence once. See the [CLI dry-run contract](filesystem-host-boundary-v1.md#cli-dry-run-292).
- Save/`format` never block on these source-only warnings; canonical write escapes the literal text, and checking that output produces no warning. Add the definition before writing to retain footnote intent, or escape the source explicitly to mark literal text. **Known boundary:** Editor Save has no corresponding warning in this change and can still silently commit this text as literal. Newly supplied Markdown-looking text in CLI operation arguments is also literal input and has no original-source evidence to warn from; use explicit Core footnote inline content or `insert-footnote` to author a footnote.

## Core

- **One placement rule**: `endnoteOrder` (`@ieumdoc/core/numbering`, no MyST dependency) is the only ordering policy. `endnotePlacement` applies it to a MyST tree at the two boundaries:
  - **Parse** gives each kept definition its own source lines (the text is tokenized once more without the rule that moves definitions) and places the definitions after the body. A parsed document, its read model and its block indexes therefore have canonical order, whatever the source placement.
  - **Canonical write** (`serialize`, used by Save, Source, `format` and every CLI write) places the definitions again before writing and verifying. Operations need not keep definitions in place.
- **Source placement**: `endnotesInPlace(document)` reports whether a parsed snapshot's definitions are already where canonical write puts them. When false, the first write moves them; nothing is written by reading.
- **Body end** (#280): public `bodyEndIndex(document)` returns the top-level insertion index before trailing endnote definitions. Without definitions it returns the block count, including metadata; an empty native document returns 1. CLI top-level insertions use it for `--at end`, including `"at": "end"` in batches. Row/column indexes and move destinations remain numeric.
- **Dropped definitions**: an unreferenced or repeated definition that the parse dropped is recorded on the document. Canonical write refuses that document and names the footnote.
- **Write rule**: each definition must be referenced and each reference must have a definition, once per label; otherwise the reload would drop or reread them. Example: removing the last reference to `[^n]` makes Save fail with `footnote [^n] has no reference, and MyST drops an unreferenced definition`.
- **Operation checks**: an operation's round-trip check covers its own blocks. It completes the footnotes on a copy, so a paragraph with a footnote can be checked on its own and a session can pass through an intermediate state. Checks find a body block at its canonical index (`bodyIndex`) and a definition by its label, so a block inserted after the endnotes or a reordered reference does not fail the check.
- List insert/update, code block insert/update and Figure caption checks compare block count with that same completed copy, including temporary definitions for new references. The full content and canonical stability must still match; an intermediate state without real definitions remains unwritable. This supports the existing Editor Save order, which updates body blocks before inserting new definitions.
- **Inline content**: `{ kind: "footnote", label }` is inline content. The label is kept as written and matched exactly, as markdown-it-footnote matches it. Links cannot contain footnotes.
- **Read model**: a definition is an editable `footnote` block with its `label` and one paragraph of supported inline content, without footnote references. Unsupported definitions reject native admission. `footnoteNumbers` gives numbers in first-reference order.
- **Operations**:
  - `insertFootnote(document, path, offset, content)` puts a reference at a Core inline offset in an editable paragraph, heading, quote, simple admonition or table cell, and its definition with the endnotes; canonical write places it by its reference.
  - `insertFootnoteDefinition(document, index, label, content)` and `updateFootnoteDefinition(document, path, content)` write a one-paragraph definition. Its text must be non-empty and hold no footnote reference. The label must be unused and stays when the text changes. `[^1]:` with no text is not a definition in MyST, so an empty definition is refused.
  - A new label is `nextFootnoteLabel`: the smallest positive number no footnote uses. Shown numbers follow reference order, so a new footnote before others can show a number different from its label.
- **Sections**: `sectionMarker` classifies a definition as `endnote`. Definitions after the body are in no section's range, and the end of the body is a section's end. `moveSection` and `removeSection` never move or remove a definition. `removeSection` refuses, before changing anything, a removal that would leave a definition with no reference (`orphanedEndnotes`), naming it.

## Editor

The Editor presents the Core order; it does not keep a source order of its own.

- The engine document is Core's read model block for block: the endnotes region follows the body because Core's snapshot does. There is no display-only reordering, no source anchor and no conversion state; Save sends the displayed order, and canonical write places the endnotes regardless.
- **Placement while editing** (`apps/editor/src/endnotes.ts`): after each document change an appended transaction applies `endnoteOrder` to the top-level blocks, so a reference moved, added or removed moves its definition in the same history event, and selection moves with its block. A document without endnotes is not read further. Each block's references are read once and reused while the block is unchanged; numbers are computed once per engine document. Placement waits while a block holds a dirty/busy property draft whose view it would rebuild, and runs after Apply/Cancel.
- A reference is an atomic superscript chip that shows its number. Bold and italic apply to it. Clicking it selects the read-only definition and scrolls to it. A chip with no definition shows its label and is marked unresolved.
- A definition shows the same number. Clicking the number returns to the reference that invoked it; the engine maps that position through later edits and placement. If that reference was deleted or none is remembered, it goes to the first remaining reference. This navigation state is not persisted.
- A supported one-paragraph definition is read-only at rest. A single click selects it; Enter on that selection or a double-click opens that definition for in-place editing. Its selected/editing outline uses the existing interaction treatment and `aria-readonly` exposes the state. Resolved reference and citation chips retain their existing reading/navigation behavior. Inline citation/reference edit buttons and inline-math properties are available only while that definition is being edited. An unresolved reference keeps its status and tooltip in read-only mode, but clicking it does not open its editing form; it can be edited after explicitly entering the definition. While editing, inline formatting, citation and document-reference authoring work as before; Enter leaves it into body space before the region and Shift+Enter is a line break. It holds no footnote reference. Unsupported definitions are rejected at admission under the native contract above.
- Escape exits editing; an open menu or form handles Escape first. Moving selection or focus outside the definition and the formatting toolbar, slash menu or citation/reference/inline-math form opened from that definition also exits editing. Apply or Cancel returns the caret to the same definition. An inline-math draft retained after moving elsewhere follows the existing property-draft contract; its input and Apply/Remove stay disabled until the definition is explicitly reopened. The tool's originating position identifies its owning definition. The state is Editor-only and changes neither Markdown, Save, placement nor history; no Core operation or CLI command is added.
- A drop or paste that would change a read-only definition is refused even when the previous selection is elsewhere or covers the whole document; an internal drag is refused as one transaction, preserving its source too. The guard compares the actual before/after definition content, including formatting changes, rather than trusting the previous selection or positional maps alone. A whole-document selection permits deletion or replacement only when the first step actually replaces the entire document. Chromium composition can normalize that selection to the first and last content positions; its fitted first replacement also consumes the final block boundary and is permitted only with composition metadata. A drop, destination-targeted paste, partial selection or partial step does not use this exception. Explicit block deletion, Undo/Redo, endnote placement and Core-planned label/reference updates retain their existing behavior. The existing lossless-clipboard restriction still refuses cutting a whole document containing endnotes.
- `/` in supported body inline content offers **Endnote** before reference targets (`/endnote`, `/footnote`, `/미주` aliases). Paragraphs, list items (including nested lists), quotes, simple admonitions, headings, table cells and Figure captions use the same insertion path. Definitions offer citations and document references but never Endnote, following Core's ban on footnote references within definitions. The [location matrix](editor-ux-shell-v1.md#nested-inline-slash-menu-377) records the existing Core save paths. Insertion replaces the query, and a space before `/`, with a reference chip that keeps bold and italic, and an empty definition in its endnote place that starts in edit mode with the caret; one Undo removes both. Save refuses a definition left empty.
- Selecting a chip and pressing Backspace removes it. If that leaves a definition unreferenced, Save is refused with the reason.
- **Gutter controls**: an endnote has no `+` (nothing is inserted after it) and its handle does not drag; the handle opens block actions (Delete). A dragged body block lands in the body, never among the endnotes. A block added after the region (for example by clicking below the document) joins the body end.
- **Sections**: a heading's section never includes the endnotes. Delete section keeps them, and is refused with a notice naming the endnote when the section holds its last reference; the reader deletes that endnote first. Move section leaves them after the body.
- **Opening a file written otherwise**: the Host reports `endnotesInPlace`. When false, a notice says that Save writes the endnotes after the body in first-reference order, keeping labels and text. Opening writes nothing and the document is not dirty; Save stays available, Source shows the Markdown Save writes, and the notice ends with the first successful Save.

### Endnotes presentation

While a definition is explicitly being edited, Ctrl/Cmd+A first selects that
definition's inline body, including line breaks; a consecutive second press
selects the document. Other definitions and the number are excluded from the
first selection. At rest, Ctrl/Cmd+A retains the existing whole-document behavior
and does not open editing or change input guards. See [scoped selection](document-editing-v1.md#select-all-within-an-editing-surface-723)
for empty bodies, composition and history (#723).

All top-level definitions follow the body in the one editor state. The first has a subtle 1px rule, a 12/16px muted `미주` label, and 24px space from the body; subsequent definitions have an 8px gap. Text keeps the 16px font and 1.5 line-height (24px), normal document text color and baseline number in a 24px inset. Inline reference chips stay superscript. The `미주` label is display only: it is not a heading, an Outline entry, selected text or Markdown. Whole-definition copying keeps the existing lossless-copy restriction; Source remains available for copying actual Markdown.

## Scope

- CLI: `insert-footnote <file> --path <indexes> --offset <n> (--text|--content)` and `update-footnote <file> --path <index> (--text|--content)` run the operations. `inspect` lists each definition as `footnote label=… inlineEditable=…`. References are also written with `--content` `{"kind":"footnote","label":"…"}`. Every write, including `format`, places the endnotes. `check` notes a document whose definitions a write would move (JSON `endnotes.inPlace`) and reports a definition MyST would drop; `check` and `format` do not write a refused document.
- CLI sections: `move-section` and `remove-section` follow the section rule above; `--to` accepts the end of the body or the block count.
- The Editor inserts footnotes from `/` on the body surfaces listed above. The dedicated CLI `insert-footnote` command addresses paragraphs, headings, quotes, simple admonitions and table cells (`--path table,row,cell`). Lists and Figure/Table captions use their typed content operations; the Editor uses those save paths without adding a Core operation or CLI command. Table captions are direct inline editing surfaces with the same slash menu as Figure captions.
- Not included: removing a definition together with its last reference (cutting and pasting a paragraph would lose its definitions; Save names the definition instead), renaming labels, a shortcut or toolbar button, keyboard navigation between a reference and its definition beyond the caret. Inline footnotes (`^[...]`) are not enabled in myst-parser.

## Changes from v3 (#194)

- v3 kept each definition where the source wrote it: Save rebuilt that placement from opening-snapshot anchors, and an explicit **미주로 모으기** command (Editor) or `collect-endnotes` (CLI, never released) moved definitions. v4 removes the anchors, the command, the `collectEndnotes` save field and the `endnotesInSource` state: the placement is canonical and applies on every write.
- A file with definitions within the body is rewritten on its first Save (or `format`), as the Open notice and Source say.
- In v3 the last section included the trailing definitions, so moving or deleting it moved or deleted them. Sections now exclude them.
